## How RAG Works In This App

Before I explain the code, let me explain the mental model. RAG has two phases:

**Phase 1 — Indexing (runs once)**
```
my_notes.md  →  split into chunks  →  embed each chunk  →  store in Neon pgvector
```

**Phase 2 — Retrieval + Generation (runs on every question)**
```
user question  →  embed question  →  find similar chunks in Neon  →  send chunks + question to Groq  →  return answer
```

The key insight: the LLM never "reads" your files. It only reads the 3–5 most relevant chunks retrieved by vector similarity. That's what keeps it accurate and fast.

## Step 1 — Setting Up Neon with pgvector

Neon is a serverless Postgres database with built-in support for the `pgvector` extension. You get a free tier with 512MB storage — more than enough for this use case.

```sql
-- Enable the extension
CREATE EXTENSION IF NOT EXISTS vector;

-- Create the table for storing embeddings
CREATE TABLE documents (
  id SERIAL PRIMARY KEY,
  content TEXT,
  embedding vector(384),  -- 384 dimensions for all-MiniLM-L6-v2
  source TEXT,            -- which .md file it came from
  metadata JSONB
);

-- Create an index for fast similarity search
CREATE INDEX ON documents USING ivfflat (embedding vector_cosine_ops)
  WITH (lists = 100);
```

The `vector(384)` type is what pgvector adds. It stores a list of 384 numbers that mathematically represents the meaning of a text chunk.

## Step 2 — The Indexing Script (FastAPI + HuggingFace)

```python
# ingest.py
from sentence_transformers import SentenceTransformer
import psycopg2
import os
import glob

model = SentenceTransformer('all-MiniLM-L6-v2')  # free, runs locally, 384 dims

def chunk_text(text: str, chunk_size: int = 500, overlap: int = 50):
    """Split text into overlapping chunks."""
    words = text.split()
    chunks = []
    for i in range(0, len(words), chunk_size - overlap):
        chunk = ' '.join(words[i:i + chunk_size])
        chunks.append(chunk)
    return chunks

def ingest_markdown_files(folder_path: str):
    conn = psycopg2.connect(os.environ['DATABASE_URL'])
    cur = conn.cursor()

    md_files = glob.glob(f"{folder_path}/**/*.md", recursive=True)
    print(f"Found {len(md_files)} markdown files")

    for file_path in md_files:
        with open(file_path, 'r', encoding='utf-8') as f:
            content = f.read()

        chunks = chunk_text(content)
        embeddings = model.encode(chunks)  # batch encode all chunks

        for chunk, embedding in zip(chunks, embeddings):
            cur.execute(
                "INSERT INTO documents (content, embedding, source) VALUES (%s, %s, %s)",
                (chunk, embedding.tolist(), file_path)
            )

    conn.commit()
    cur.close()
    conn.close()
    print("Ingestion complete!")

if __name__ == "__main__":
    ingest_markdown_files("./interview_prep")
```

I ran this once locally. It processed all my markdown files, split them into 500-word chunks with 50-word overlap (so context isn't cut off at boundaries), and stored the embeddings in Neon.

**Why HuggingFace `all-MiniLM-L6-v2`?**
- Completely free, no API key needed
- 384-dimensional vectors (smaller = faster search)
- Great quality for technical Q&A retrieval
- Used in thousands of production RAG systems

## Step 3 — The FastAPI Backend

```python
# main.py
from fastapi import FastAPI
from fastapi.middleware.cors import CORSMiddleware
from pydantic import BaseModel
from sentence_transformers import SentenceTransformer
from groq import Groq
import psycopg2
import os

app = FastAPI()
app.add_middleware(CORSMiddleware, allow_origins=["*"], allow_methods=["*"], allow_headers=["*"])

embed_model = SentenceTransformer('all-MiniLM-L6-v2')
groq_client = Groq(api_key=os.environ['GROQ_API_KEY'])

class ChatRequest(BaseModel):
    question: str

@app.post("/chat")
async def chat(request: ChatRequest):
    # 1. Embed the question
    question_embedding = embed_model.encode(request.question).tolist()

    # 2. Find top 5 similar chunks from Neon
    conn = psycopg2.connect(os.environ['DATABASE_URL'])
    cur = conn.cursor()
    cur.execute("""
        SELECT content, source, 1 - (embedding <=> %s::vector) AS similarity
        FROM documents
        ORDER BY embedding <=> %s::vector
        LIMIT 5
    """, (question_embedding, question_embedding))
    
    results = cur.fetchall()
    cur.close()
    conn.close()

    # 3. Build context from retrieved chunks
    context = "\n\n---\n\n".join([row[0] for row in results])

    # 4. Send to Groq (Llama 3) with context
    response = groq_client.chat.completions.create(
        model="llama3-8b-8192",
        messages=[
            {
                "role": "system",
                "content": """You are a Java interview coach. Answer the question using ONLY 
                the context provided from the candidate's personal notes. Be concise and clear.
                If the answer isn't in the context, say so honestly."""
            },
            {
                "role": "user",
                "content": f"Context:\n{context}\n\nQuestion: {request.question}"
            }
        ]
    )

    return {
        "answer": response.choices[0].message.content,
        "sources": [row[1] for row in results]  # which .md files were used
    }
```

The `<=>` operator in the SQL query is pgvector's cosine distance operator. Lower distance = more similar. The query finds the 5 most semantically similar chunks to the user's question in milliseconds.

## Step 4 — The Next.js Frontend

The frontend is straightforward — a chat interface that calls the FastAPI backend.

```typescript
// app/api/chat/route.ts  — proxies to FastAPI to hide the backend URL
export async function POST(request: Request) {
  const body = await request.json()
  
  const response = await fetch(`${process.env.FASTAPI_URL}/chat`, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify(body)
  })
  
  const data = await response.json()
  return Response.json(data)
}
```

```typescript
// components/ChatInterface.tsx (simplified)
'use client'
import { useState } from 'react'

export default function ChatInterface() {
  const [messages, setMessages] = useState<Message[]>([])
  const [input, setInput] = useState('')
  const [loading, setLoading] = useState(false)

  async function sendMessage() {
    if (!input.trim()) return
    setLoading(true)
    
    const userMessage = { role: 'user', content: input }
    setMessages(prev => [...prev, userMessage])
    setInput('')

    const res = await fetch('/api/chat', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({ question: input })
    })
    
    const data = await res.json()
    setMessages(prev => [...prev, { role: 'assistant', content: data.answer }])
    setLoading(false)
  }

  return (
    <div className="chat-container">
      <div className="messages">
        {messages.map((m, i) => (
          <div key={i} className={`message ${m.role}`}>{m.content}</div>
        ))}
        {loading && <div className="message assistant">Thinking...</div>}
      </div>
      <div className="input-row">
        <input value={input} onChange={e => setInput(e.target.value)}
          onKeyDown={e => e.key === 'Enter' && sendMessage()}
          placeholder="Ask a Java interview question..." />
        <button onClick={sendMessage}>Ask Coach</button>
      </div>
    </div>
  )
}
```

## What I Learned

### 1. Chunk overlap matters more than I expected
My first attempt had no overlap between chunks. Questions that spanned a Q&A boundary in the markdown (like a multi-part answer) would get cut off. Adding 50-word overlap fixed this.

### 2. The system prompt is critical
Without a strong system prompt saying "only use the provided context," the LLM would happily answer from its training data and ignore my notes entirely. RAG only works if you explicitly constrain the model.

### 3. Groq is genuinely fast
I expected latency. Groq returns answers in under 2 seconds. Their custom LPU (Language Processing Unit) hardware is not a gimmick — it's noticeably faster than OpenAI's API for the same model quality.

### 4. Neon's free tier is production-ready
No cold starts, global edge replicas, branch-based dev/prod workflow. For a side project this size it's effectively free infrastructure with zero management overhead.

### 5. Vector search ≠ keyword search
The most satisfying moment: I asked *"what's the difference between notify() and notifyAll()?"* — and it correctly retrieved chunks about Java threading even though the words "notify" and "notifyAll" didn't appear verbatim in every chunk. That's vector similarity at work.
